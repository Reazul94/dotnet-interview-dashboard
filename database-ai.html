2. DATABASE NORMALIZATION & DENORMALIZATION ২. ডাটাবেজ নরম্যালাইজেশন এবং ডিনরম্যালাইজেশন

1NF (First Normal Form): Atomic values per cell (no multi-valued columns or repeating groups). ১এনএফ (১ম নরমাল ফর্ম): প্রতিটি সেলে একক মান (কোনো মাল্টি-ভ্যালু কলাম বা গ্রুপ থাকবে না)।

2NF (Second Normal Form): In 1NF + No partial dependencies (all non-key columns fully dependent on primary key). ২এনএফ (২য় নরমাল ফর্ম): ১এনএফ মেনে চলবে + আংশিক নির্ভরশীলতা থাকবে না।

3NF (Third Normal Form): In 2NF + No transitive dependencies (non-key columns depend ONLY on primary key). ৩এনএফ (৩য় নরমাল ফর্ম): ২এনএফ মেনে চলবে + ট্রানজিটিভ নির্ভরশীলতা থাকবে না।

BCNF (Boyce-Codd Normal Form): Strict 3NF variant where every determinant is a candidate key. বিসিএনএফ: ৩এনএফ এর কঠোর সংস্করণ যেখানে প্রতিটি ডিটারমিন্যান্ট ক্যান্ডিডেট কী।

❌ Bad Design (Unnormalized): ❌ খারাপ ডিজাইন (ডিনরম্যালাইজড): 

CustomerID | CustomerName | Product1 | Product2 | Product3

✅ Normalized Design: ✅ সঠিক নরম্যালাইজড ডিজাইন: 

Customer   (CustomerID, CustomerName, Email)
Order      (OrderID, CustomerID, OrderDate)
OrderItem  (OrderItemID, OrderID, ProductID, Quantity, Price)
Product    (ProductID, ProductName, Price)
Q: Why normalization helps & when would you intentionally denormalize? প্রশ্ন: নরম্যালাইজেশন কেন প্রয়োজন এবং কখন আপনি ইচ্ছা করে ডিনরম্যালাইজ করবেন?
"Normalization reduces data duplication, maintains consistency, makes updates easier, and enforces data integrity.

Intentionally Denormalize: In read-heavy systems, reporting data marts, analytics, or performance-critical APIs to reduce expensive multi-table JOINs.
Trade-off: Duplicated data can lead to data consistency problems and requires update triggers/synchronization code." "নরম্যালাইজেশন ডেটা ডুপ্লিকেশন কমায়, কনসিস্টেন্সি বজায় রাখে এবং আপডেট সহজ করে। রিড-হেভি সিস্টেম, রিপোর্টিং ও পারফরম্যান্স বাড়াতে JOIN কমাতে ডিনরম্যালাইজ করা হয়। তবে এতে ডুপ্লিকেট ডেটার কারণে ডাটা অসামঞ্জস্যতার ঝুঁকি থাকে।"

3. INDEXING MASTER CLASS ৩. ইনডেক্সিং মাস্টার ক্লাস

★★★★★ HIGH PRIORITY ★★★★★ অতি জরুরী
Analogy: How does a Database Index work? বাস্তব উদাহরণ: ডাটাবেজ ইনডেক্স কীভাবে কাজ করে?
"Without Index: Reading an unindexed table is like searching for a phrase in a 1,000-page book by scanning every single line page-by-page (Table Scan).
With Index: Using a B-Tree index is like turning directly to the alphabetical index at the back of the book to jump directly to page 412 (Index Seek)." "ইনডেক্স ছাড়া: ইনডেক্সহীন টেবিল পড়া ১,০০০ পৃষ্ঠার বইয়ের প্রতিটি লাইন লাইন স্ক্যান করার মতো (Table Scan)।
ইনডেক্স সহ: B-Tree ইনডেক্স ব্যবহার বইয়ের পেছনের সূচিপত্র দেখে সরাসরি নির্দিষ্ট পৃষ্ঠায় চলে যাওয়ার মতো (Index Seek)।"
Index Type Concept & Mechanism Key Characteristic
Clustered Index Physically sorts and stores table data rows on disk in index order. ডিস্কে ডাটা শারীরিকভাবে ইনডেক্স ক্রমানুসারে সাজিয়ে রাখে। Only ONE per table (Primary Key default). প্রতি টেবিলে কেবল ১টি থাকে।
Non-Clustered Index Separate index structure containing key values + row pointers. মূল ডাটা ছাড়া আলাদা ইনডেক্স স্ট্রাকচার ও পয়েন্টার। Can have multiple (e.g. 249 per table). একাধিক তৈরি করা যায়।
Composite Index Index created on multiple columns e.g. (Name, Status). একাধিক কলামের সমন্বয়ে তৈরি ইনডেক্স। Column ordering matters (Leftmost prefix). কলামের ক্রম অত্যন্ত গুরুত্বপূর্ণ।
Covering Index Index containing all requested query columns in leaf nodes. কুয়েরির প্রয়োজনীয় সব কলাম ধারণ করে। Avoids base table Key Lookups. টেবিল লুকআপ সম্পূর্ণ এড়ায়।
⚠️ IMPORTANT: INDEXES ARE NOT ALWAYS BENEFICIAL! ⚠️ সব সময় ইনডেক্স ব্যবহারে লাভ হয় না!
"Indexes speed up SELECT queries, BUT they slow down INSERT, UPDATE, and DELETE operations because every write must also modify the B-Tree index pages. They also consume disk storage and increase maintenance/fragmentation rebuild costs." "ইনডেক্স SELECT দ্রুত করে, কিন্তু অতিরিক্ত ইনডেক্স INSERT, UPDATE ও DELETE অপারেশনকে ধীরগতির করে কারণ প্রতিটি রাইটে ইনডেক্স আপডেট করতে হয়।"

4. COMPOSITE INDEX & LEFTMOST PREFIX ৪. কম্পোজিট ইনডেক্স এবং লেফটমোস্ট প্রিপিক্স 

CREATE INDEX IX_Customer_Name_Status ON Customer(Name, Status);
Q: Does an index on (A, B) automatically make filtering by B efficient? প্রশ্ন: (A, B) কলামের ইনডেক্স কি শুধু B দিয়ে ফিল্টার করলে দ্রুত কাজ করবে?
"Not necessarily. A B-tree composite index is ordered primarily by column A, then secondary by column B. Filtering by A or A + B naturally utilizes the index seek. Filtering only by B forces a scan unless the optimizer chooses a full index scan or skip scan." "না, সব সময় নয়। B-tree কম্পোজিট ইনডেক্স প্রথমে A এবং পরে B ক্রমানুসারে সাজানো থাকে। শুধু B দিয়ে ফিল্টার করলে ইনডেক্স সিক কাজ করে না।"

5. COVERING INDEX ৫. কভারিং ইনডেক্স

A covering index contains enough indexed/included data for a query so the database can answer the query directly from the index leaf nodes, avoiding going back to the base table (eliminating Key / RID Lookups). কভারিং ইনডেক্স কুয়েরির কাঙ্ক্ষিত সব কলাম ইনডেক্সেই ধারণ করে, ফলে ডাটাবেজকে মূল টেবিলে লুকআপ করতে হয় না। 

-- Query:
SELECT CustomerId, Name FROM Customer WHERE Email = 'user@example.com';

-- Covering Index Definition:
CREATE NONCLUSTERED INDEX IX_Customer_Email
ON Customer(Email) INCLUDE (Name);

6. WHY IS MY INDEX NOT BEING USED? (10 REASONS) ৬. কেন ইনডেক্স কাজ করছে না? (১০টি কারণ)

  1. 1. Function applied to indexed column: WHERE LOWER(Name) = 'john' (Non-SARGable). ১. কলামের উপর ফাংশন ব্যবহার: WHERE LOWER(Name) = 'john' ইনডেক্স ব্যবহার এড়ায়।
  2. 2. Poor selectivity: Column has very few unique values (e.g., Boolean Gender). ২. কম সিলেকটিভিটি: কলামে একই ভ্যালু বারবার থাকা।
  3. 3. Small table: Database optimizer decides a Table Scan is faster than Index Seek + Lookup. ৩. ছোট টেবিল: টেবিল ছোট হলে অপটিমাইজার টেবিল স্ক্যানই পছন্দ করে।
  4. 4. Outdated statistics: Query optimizer generates a poor execution plan based on stale stats. ৪. পুরানো স্ট্যাটিস্টিকস: ডাটাবেজ স্ট্যাটস আপডেট না থাকা।
  5. 5. Implicit type conversion: Passing VARCHAR literal to an NVARCHAR indexed column. ৫. ইনপ্লিসিট টাইপ কনভার্সন: টাইপ অসঙ্গতি।
  6. 6. Leading wildcard in LIKE: WHERE Name LIKE '%John' forces full scan. ৬. সামনে ওয়াইল্ডকার্ড ব্যবহার: WHERE Name LIKE '%John' স্ক্যান বাধ্য করে।

8. EXECUTION PLAN OPERATORS ৮. এক্সিকিউশন প্ল্যান উপাদানসমূহ

Operator Mechanism Is It Bad?
Index Seek Navigates B-Tree directly to specific rows. ইনডেক্স ধরে সরাসরি নির্দিষ্ট সারিতে যায়। Usually Best (Targeted lookup) সবচেয়ে দ্রুত ও সেরা
Index Scan Traverses all pages of the index. ইনডেক্সের সব পেজ স্ক্যান করে। Can be inefficient for large tables বড় টেবিলে ধীরগতির হতে পারে
Table Scan Reads all rows of a heap table. টেবিলের সব ডাটা পড়তে বাধ্য হয়। Not bad for small tables (< 1,000 rows) ছোট টেবিলে খারাপ নয়

10. JOIN OPTIMIZATION & INTERVIEW FRAMEWORK ১০. জয়েন অপটিমাইজেশন এবং উত্তর দেওয়ার ফ্রেমওয়ার্ক

Q: "Why is my JOIN query slow?" (8-Step Framework) প্রশ্ন: "আমার JOIN কুয়েরি কেন ধীরগতির?" (৮টি ধাপ)
"1. Check Execution Plan → 2. Check Join Columns for Indexes → 3. Check Join Cardinality → 4. Verify Row Counts → 5. Check if Filtering occurs BEFORE Joining → 6. Update Statistics → 7. Check Join Algorithm (Nested Loop vs Hash vs Merge) → 8. Eliminate Unnecessary Joins." "১. এক্সিকিউশন প্ল্যান দেখুন → ২. জয়েন কলামে ইনডেক্স চেক করুন → ৩. কার্ডিনালিটি দেখুন → ৪. রিকোর্ডের সংখ্যা পরীক্ষা করুন → ৫. জয়েন করার আগেই ফিল্টার করার চেষ্টা করুন → ৬. স্ট্যাটস আপডেট করুন → ৭. জয়েন অ্যালগরিদম পরীক্ষা করুন → ৮. অপ্রয়োজনীয় জয়েন দূর করুন।"

11. N+1 QUERY PROBLEM IN ORMs ১১. ওআরএম-এ N+1 কুয়েরি সমস্যা

Q: What is the N+1 Query Problem? প্রশ্ন: N+1 কুয়েরি সমস্যা কী?
"N+1 occurs when an ORM (EF Core / Hibernate) executes 1 query to fetch a parent list of N items (e.g., 100 Customers), then executes N separate database queries inside a loop to fetch child records for each customer. Total queries executed: 1 + 100 = 101 queries!

Solutions: Eager Loading (.Include() in EF Core / JOIN FETCH in JPA), Projections, Explicit JOINs, or Batch Loading." "N+1 সমস্যা ঘটে যখন ওআরএম প্যারেন্ট লিস্ট আনতে ১টি কুয়েরি চালায় এবং প্রতিটি আইটেমের জন্য লুপের ভেতরে আরও Nটি আলাদা কুয়েরি চালায় (যেমন: ১ + ১০০ = ১০১টি কুয়েরি!)।
সমাধান: Eager Loading (.Include()), Projections বা Explicit JOINs ব্যবহার করা।"

12. TRANSACTIONS & ACID PROPERTIES ১২. ট্রানজেকশন এবং ACID বৈশিষ্ট্য

A — Atomicity: All operations succeed or all fail. অ্যাটোরমিসিটি: সব সফল হবে অথবা সব ব্যর্থ হবে।
C — Consistency: Valid state transitions. কনসিস্টেন্সি: ডাটা সব সময় বৈধ থাকবে।
I — Isolation: Transactions execute independently. আইসোলেশন: একটি অন্যটিকে প্রভাবিত করবে না।
D — Durability: Committed data persists permanently. ডিউরেবিলিটি: ডাটা স্থায়ীভাবে সংরক্ষিত থাকবে।

14. DEADLOCK PREVENTION ১৪. ডেডলক প্রতিরোধ ও সমাধান

Q: How do you prevent and handle deadlocks? প্রশ্ন: কীভাবে ডেডলক এড়াবেন এবং হ্যান্ডেল করবেন?
"1. Access tables in consistent chronological order across all transactions.
2. Keep transactions short; do not make external HTTP API calls inside a transaction.
3. Use appropriate indexes to minimize scan lock duration.
4. Enable Read Committed Snapshot Isolation (RCSI) in SQL Server.
5. Implement retry logic for transient deadlock errors (Error 1205)." "১. সব ট্রানজেকশনে একই ক্রমানুসারে টেবিল অ্যাক্সেস করুন।
২. ট্রানজেকশন ছোট রাখুন এবং ভেতরে কোনো External HTTP API কল করবেন না।
৩. সঠিক ইনডেক্স ব্যবহার করে লকিং টাইম কমান।
৪. RCSI অন রাখুন।
