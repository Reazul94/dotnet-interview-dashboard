2. DATABASE NORMALIZATION & DENORMALIZATION

1NF (First Normal Form): Atomic values per cell (no multi-valued columns or repeating groups).

2NF (Second Normal Form): In 1NF + No partial dependencies (all non-key columns fully dependent on whole primary key).

3NF (Third Normal Form): In 2NF + No transitive dependencies (non-key columns depend ONLY on primary key, not on other non-key columns).

BCNF (Boyce-Codd Normal Form): Strict 3NF variant where every determinant is a candidate key.

❌ Bad Design (Unnormalized):

CustomerID | CustomerName | Product1 | Product2 | Product3

✅ Normalized Design:

Customer   (CustomerID, CustomerName, Email)
Order      (OrderID, CustomerID, OrderDate)
OrderItem  (OrderItemID, OrderID, ProductID, Quantity, Price)
Product    (ProductID, ProductName, Price)
Q: Why normalization helps & when would you intentionally denormalize?
"Normalization reduces data duplication, maintains consistency, makes updates easier, and enforces data integrity.

Intentionally Denormalize: In read-heavy systems, reporting data marts, analytics, or performance-critical APIs to reduce expensive multi-table JOINs.
Trade-off: Duplicated data can lead to data consistency problems and requires update triggers/synchronization code."

3. INDEXING MASTER CLASS

★★★★★ HIGH PRIORITY
Analogy: How does a Database Index work?
"Without Index: Reading an unindexed table is like searching for a phrase in a 1,000-page book by scanning every single line page-by-page (Table Scan).
With Index: Using a B-Tree index is like turning directly to the alphabetical index at the back of the book to jump directly to page 412 (Index Seek)."
Index Type Concept & Mechanism Key Characteristic
Clustered IndexPhysically sorts and stores table data rows on disk in index order.Only ONE per table (Primary Key by default).
Non-Clustered IndexSeparate index structure containing key values + row pointers (RID/Clustered Key).Can have multiple (e.g. 249 per table).
Composite IndexIndex created on multiple columns e.g. (Name, Status).Column ordering matters (Leftmost prefix).
Unique IndexEnforces unique value constraint while indexing.Prevents duplicate key entries.
Covering IndexIndex containing all requested query columns in leaf nodes.Avoids base table Key Lookups.
Filtered / Partial IndexIndex with a WHERE clause indexing subset of rows.Saves disk space (e.g. WHERE IsActive = 1).
⚠️ IMPORTANT: INDEXES ARE NOT ALWAYS BENEFICIAL!
"Indexes speed up SELECT queries, BUT they slow down INSERT, UPDATE, and DELETE operations because every write must also modify the B-Tree index pages. They also consume disk storage and increase maintenance/fragmentation rebuild costs."

4. COMPOSITE INDEX & LEFTMOST PREFIX

CREATE INDEX IX_Customer_Name_Status ON Customer(Name, Status);
Q: Does an index on (A, B) automatically make filtering by B efficient?
"Not necessarily. A B-tree composite index is ordered primarily by column A, then secondary by column B (like a phonebook ordered by Last Name, then First Name). Filtering by A or A + B naturally utilizes the index seek. Filtering only by B forces a scan unless the optimizer chooses a full index scan or skip scan."

5. COVERING INDEX

A covering index contains enough indexed/included data for a query so the database can answer the query directly from the index leaf nodes, avoiding going back to the base table (eliminating Key / RID Lookups). 

-- Query:
SELECT CustomerId, Name FROM Customer WHERE Email = 'user@example.com';

-- Covering Index Definition:
CREATE NONCLUSTERED INDEX IX_Customer_Email
ON Customer(Email) INCLUDE (Name);

6. WHY IS MY INDEX NOT BEING USED? (10 REASONS)

  1. 1. Function applied to indexed column: WHERE LOWER(Name) = 'john' (Non-SARGable).
  2. 2. Poor selectivity: Column has very few unique values (e.g., Boolean Gender).
  3. 3. Small table: Database optimizer decides a Table Scan is faster than Index Seek + Lookup.
  4. 4. Outdated statistics: Query optimizer generates a poor execution plan based on stale stats.
  5. 5. Implicit type conversion: Passing VARCHAR literal to an NVARCHAR indexed column.
  6. 6. Leading wildcard in LIKE: WHERE Name LIKE '%John' forces full scan.
  7. 7. Query returns large percentage of table: Optimizer chooses scan over millions of key lookups.
  8. 8. Incorrect composite index column order: Filtering by non-leading composite column.
  9. 9. Optimizer estimates scan is cheaper: Hardware/memory statistics suggest scan cost is lower.
  10. 10. Query structure issues: Complex OR conditions across unindexed columns.

11. N+1 QUERY PROBLEM IN ORMs

Q: What is the N+1 Query Problem?
"N+1 occurs when an ORM (EF Core / Hibernate) executes 1 query to fetch a parent list of N items (e.g., 100 Customers), then executes N separate database queries inside a loop to fetch child records for each customer. Total queries executed: 1 + 100 = 101 queries!

Solutions: Eager Loading (.Include() in EF Core / JOIN FETCH in JPA), Projections, Explicit JOINs, or Batch Loading."

12. TRANSACTIONS & ACID PROPERTIES

A — Atomicity: All operations succeed or all fail.
C — Consistency: Database transitions from one valid state to another.
I — Isolation: Concurrent transactions do not interfere with each other.
D — Durability: Committed data persists permanently even after power failure.

14. DEADLOCK PREVENTION

Q: How do you prevent and handle deadlocks?
"1. Access tables in consistent chronological order across all transactions.
2. Keep transactions short; do not make external HTTP API calls inside a transaction.
3. Use appropriate indexes to minimize scan lock duration.
4. Enable Read Committed Snapshot Isolation (RCSI) in SQL Server.
5. Implement retry logic for transient deadlock errors (Error 1205)."

16. COMMON TABLE EXPRESSION (CTE)

WITH CustomerOrders AS (
    SELECT CustomerId, COUNT(*) AS OrderCount
    FROM Orders
    GROUP BY CustomerId
)
SELECT * FROM CustomerOrders WHERE OrderCount > 5;

17. WINDOW FUNCTIONS (ROW_NUMBER, RANK, LAG, LEAD)

SELECT CustomerId, OrderDate, TotalAmount,
       ROW_NUMBER() OVER (PARTITION BY CustomerId ORDER BY OrderDate DESC) AS RowNum
FROM Orders;
